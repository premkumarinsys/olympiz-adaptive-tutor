## What the current actual run shows

The export was generated by executing Asha, Meera, Rohan, and Isha through the real `TutorRuntime`. It produced four agent traces and three renderer prompt events. Isha's unsupported-content scenario safely refused before the renderer, so it correctly has a trace but no prompt event.

No `OPENAI_API_KEY` was configured. Therefore, the three prompt events explicitly record:

```json
{
  "event_type": "llm_call_skipped",
  "provider_called": false,
  "outcome": "skipped",
  "skip_reason": "OPENAI_API_KEY_NOT_CONFIGURED",
  "response": null
}
```

This is intentional and honest: the request object is the exact bounded payload generated by the application, but no provider response is claimed or fabricated.

## Logging behavior

The application now writes append-only runtime records to:

```text
backend/data/runtime/prompt_logs/llm-calls.jsonl
```

For a live call, each record contains the exact request, response ID, response model, structured output, token usage when supplied, validation result, safe error type, duration, plan/input hashes, and request/response hashes. For a template-mode run, it records the exact request that was skipped and the reason.

The logger never stores the API key, learner identifier, or raw learner history. Prompt records correlate with agent traces through `plan_hash`.

## Reproduce the submitted bundle

```powershell
cd D:\olympiz-adaptive-tutor\backend
.\.venv\Scripts\python.exe scripts\generate_application_logs.py
```

The generator deliberately disables live provider access so it cannot create an accidental bill or misrepresent a recorded response. Starting the normal backend with `OPENAI_API_KEY` enables real request/response logging through the same code path.
